## 2. 从研究问题与信息条件开始，而不是从模块名单开始

请像共同推导一样，从少量符号和清楚的定义逐步展开：

- 数据与functional训练目标能确定什么，不能唯一确定什么？
- 哪些内部语义只是可选解释，哪些行为性质才是必须验证的目标？

## 3. 逐步推导需要的职责、表示和参数生成

从上述信息与目标推出必要职责，再讨论怎样用架构承担：

- 任务语义与视觉grounding需要保留什么？
- Action Expert原生知识应怎样参与，哪些原生轴有明确消费者？
- 视频内部的过程信息如何被使用，多视频之间哪些信息应共同保留或区分？
- 过程/任务证据如何进入真实policy参数坐标，并产生完整的一套LoRA？
- 模块之间共享什么、分开什么？这些选择影响表达范围、学习条件和成本的方式是什么？

对每一步分别标注：
1. 可由定义或数学推出的性质；
2. 依赖的假设；
3. 建模上的归纳偏置；
4. 实现选择；
5. 尚需实验确认的能力。

推导中同时使用历史成功与失败约束选择。不能因某个表示叫native、process、memory或causal，就赋予它未经证明的语义。
不能由局部oracle可达，推出真实视频条件共享映射可学；不能由一个指标更丰富，推出策略更好。

不要求提出全新架构。保留当前图、恢复某项旧职责、局部替换或改变训练，都应是论证后的选择。
如果保留或移除某个模块，说明已有证据支持什么、反对什么、仍有什么代价未知。

## 5. 把重复失败真正转化为推导约束

针对rank/能量/公共表示/能力换手等重复现象，说明：
- 它可能处于因果链的什么位置；
- 过去哪些干预已经削弱了哪一解释；
- 为什么本次仍有理由考虑某项相似选择；
- 哪种行为结果会推翻当前判断。

不能通过换一个模块名称，重新启用已经缺乏支持的假设。
也不能把过往某个预算、初始化或函数类的失败推广为整类方法永远无效。
